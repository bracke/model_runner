# What the published performance figures were measured against.
#
# The README publishes numbers that were measured, not derived: how long a row
# product takes per element, how long twelve tokens take, how the matrix
# product scales. They cannot be checked the way the conformance figures can,
# because they differ by half a per cent between runs and by much more between
# machines, so no assertion about their value can hold anywhere but here.
#
# What can be checked is whether they still describe this code. Each group
# below names the sources its numbers depend on and a fingerprint of those
# sources as they stood when the numbers were taken. `tests check` recomputes
# the fingerprint and fails when it differs, which means: these sources have
# changed since the figures were published, so either re-measure and record
# what you get, or say why the change cannot have moved them.
#
# That is a duty, and the point of putting it here is that it is a duty the
# release checklist enforces rather than one somebody has to remember. Every
# group below has gone stale once already, by two to four times.
#
# Format, one group per line:
#   <name> <fingerprint> <source> [<source> ...]
#
# The measuring tool counts as a source. Every group whose figures come from
# `tests speed` lists tests/src/speed_run.adb, because a change there changes
# the figures as surely as a change to the engine does -- and did: the tool
# read the prompt file differently from the command and sampled differently
# from it, for as long as it had existed, and nothing here noticed because
# nothing here was watching the thing doing the measuring.
#
# The "# The host every figure below was taken on, which none of them said.
#
#   processor  AMD Ryzen 7 7840U with Radeon 780M Graphics, 16 hardware
#              threads
#   device     AMD Radeon 780M Graphics (RADV PHOENIX), integrated, one
#              queue in the family the engine computes on. A second device
#              is listed, llvmpipe, which is a software renderer and not
#              what any of these figures used.
#   system     Linux 6.17.0, GNAT from the toolchain this repository pins
#
# A figure without its host is a figure about nothing: 1.871 s for twelve
# tokens says something only beside the machine that took 1.871 s. The load
# each run carried has been recorded here for months and what carried it
# never was, which is half a condition written down twice.

# 2026-08-17, the shape behind the sweep's totals, which it now prints: nine
# architectures, fifteen formats and five shapes, with 864 of the 24939
# sequences run on a device. A total says nothing about what it covers, and
# what it covers is the whole of the claim the number is quoted for.
#
# The gate is bounded as a whole as well as stage by stage -- 1500 s against
# the twelve minutes it takes -- because four stages each inside their own
# bound still add to a run nobody notices growing, which is exactly how half
# an hour became an hour.

# 2026-08-17, what the reference's remaining time is. With one load a
# fixture, its 397 s divides into 274.7 s decoding each fixture into
# binary64 and 122.7 s computing with it -- so decoding is sixty-nine per
# cent of the reference and about forty-five per cent of the whole sweep,
# and it is already one pass a fixture. That is the floor of having a second
# implementation in a wider format, and it is where it should be rather than
# somewhere nobody looked.
#
# The gate holds each stage to roughly twice what it took here and fails
# when one exceeds it -- repository checks 30 s, conformance 1250 s,
# fixtures 200 s, fuzzing 10 s. Twice, because a busy machine takes half
# again as long and that is not news, while a stage that doubles has had
# something added to it. The gate went from half an hour to an hour once and
# nothing said so until somebody timed it by hand.

# 2026-08-17, the sweep loaded the reference four times a fixture. Splitting
# its cost by sequence is what found it: the four sequences cost 281, 289,
# 310 and 333 seconds across a sweep though they are one, two, five and eight
# tokens long. Costs that flat under an eightfold difference in work are not
# the work -- they are the load, which is every matrix of the fixture decoded
# into binary64, done once for each sequence asked about.
#
# One load a fixture now, running all four. The sweep went from 1431 s to
# 599 s, and the reference within it from 1213 s to 386 s, on the same
# figures to the digit: 24939 sequences, none outside tolerance, none
# unlearned. The gate is about eleven minutes where it was twenty-five.
#
# The parallelism I had written down as the next thing is not needed for
# this, and would have bought a quarter of what a second glance at the
# measurement did.

# 2026-08-17, where the sweep's twenty-four minutes go, which it now says:
#
#   fixtures built          59.9 s    4 per cent
#   the reference         1206.9 s   85 per cent
#   the engine             ~157   s   11 per cent
#
# The independent implementation is eighty-five per cent of the sweep, and
# the sweep is ninety-four per cent of the gate: four fifths of every gate
# run is one binary64 transformer computing what a binary32 one has already
# computed. That is the price of having a second implementation and it is
# the point of having one, so it is not waste -- but anybody who sets out to
# make the gate faster should know they are being asked to make the
# reference faster, and nothing else will matter.
#
# It already runs once a fixture rather than once a comparison: caching that
# took the sweep from nine minutes to two when it was written. What is left
# is four sequences a fixture, each independent of the others and each on one
# task.
#
# 2026-08-17, what the gate costs, stage by stage, as it now says itself:
#
#   repository checks     10.1 s
#   conformance         1425.1 s
#   fixtures              77.4 s
#   fuzzing                0.1 s
#
# Conformance is ninety-four per cent of it. That is worth knowing before
# anybody optimizes anything else: the fixture check's seventy-eight seconds
# looked like the thing that grew the gate, and it is five per cent of it.
#
# It also settles a question I had written down as work to do -- running the
# gate's halves in parallel. Overlapping the repository checks, the fixture
# check and both fuzzing campaigns with each other would save at most eighty-
# seven seconds of a twenty-five minute run, and they contend for the device
# besides. The only parallelism worth having is inside the conformance sweep,
# which is a different piece of work with a different argument.
#
# 2026-08-17, what the fixture check costs the gate. 78.3 s, the median of
# three on the host above: 76.30, 78.28 and 78.35, of which about 67 s is
# user time. It moves 22195 tensors, evaluating a tiny model twice for each.
#
# It cost 28 s when it was written, three days ago, and grew for two reasons
# worth separating: gemma3 is built with six blocks now rather than two,
# which is a third of the tensors it moves; and every fixture is also loaded
# by the independent implementation once, to compare what the file holds
# against what that implementation asks for.
#
# Not a measured figure in the sense the others are -- nothing publishes it
# and no fingerprint covers it -- but a gate that grew from thirty minutes
# is a thing somebody should be able to find the cause of, and 78 s of it is
# here.

# 2026-08-18, gpt2 on a published file. Six prompt tokens and twelve
# generated: 0.253 s wall -- 0.045 s evaluating the prompt and 0.210 s
# generating -- and 1.28 s of processor time, loading in 0.235 s, digest
# 6260472a109d3651.

# model: gpt2 Q8_0 as mradermacher published it -- gpt2.Q8_0.gguf,
# 177669376 bytes, 149 tensors, 163 million parameters, context 1024.
#
# Against TinyLlama-1.1B Q8_0's 1.871 s for the same twelve tokens. Worth

# about a seventh of the parameters, so what the figure measures is size. It
# is the first architecture here that does not rotate, and the rotation is
# too small a part of a token's work to see at this distance -- a figure
# that isolated it would have to hold the size fixed, which no pair of
# published models does.

# 2026-08-18, what a fixture has in common with a file somebody ships.
# `tests fixture-likeness --model PATH` folds layer indices together and
# compares tensor names both ways. Against the ten published files:
#
#   llama, phi2, phi3, falcon    every name on both sides
#   gpt2                         blk.*.ffn_norm.bias in the file, not in the
#                                fixture -- and not read by the engine
#   qwen2, qwen3, gemma,         output.weight written by the fixture and
#   gemma2, gemma3               carried by none of them: they tie the
#                                embedding, and no fixture here does
#
# The gpt2 line was a live defect, not a cosmetic difference. Every published
# gpt2 carries a shift beside its feed-forward normalization; the engine read
# every other layer-norm shift and not that one, and the feed-forward ran off
# a normalization that was neither centred nor shifted. Twenty-six thousand
# conformance sequences agreed with the reference throughout, because the
# reference did not read it either and the fixture did not write it. Three
# implementations sharing one wrong idea agree perfectly.
#
# The tied-embedding line is not a defect -- the engine falls back to the
# embedding when there is no output matrix, which is why those five models
# load and generate -- but it is a gap: no fixture here ties, so the fallback
# is exercised only by files a caller supplies.

# 2026-08-19, an attention kernel, checked and not yet wired.
#
# attention.comp does one position attending to everything a cache holds: the
# scores, the bound where an architecture states one, the softmax across them,
# and the values weighted by what comes out. It is the piece of a layer that
# stands between two matrix products and keeps them from being sent together,
# so it is what the rest of the resident chain waits on.
#
# Keys and values share a buffer, because attention wants four arrays and the
# pipeline layout carries three. Widening the layout would have cost every
# shader; laying the cache out as one region costs nothing, since this program
# writes the cache in the first place.
#
# One invocation a head, folding the softmax into the pass that computes the
# scores -- a running maximum, a running sum, a running weighted value -- so
# nothing is stored per position. The host does not do it that way because it
# has the scores in an array anyway; a device wants it because storing a score
# a position is storing a context length of them.
#
# Checked against the same arithmetic in binary64: worst disagreement under
# 1.0E-5 across four heads and sixteen positions. Checked by breaking it too
# -- swapping where the keys and the values begin disagrees by 1.6E-2.
#
# Not wired, and it cannot pay yet: Attend uploads the whole cache on every
# call, which is the round trip this exists to remove. What makes it worth
# having is the cache staying on the device between tokens, and that is a
# change to where the cache lives rather than to this kernel. The device
# figure is unchanged within the day's spread -- 0.596 s wall, 0.488 s
# generating, digest 5709b12b0517c8c5 -- because nothing in the engine calls
# it.

# 2026-08-18, what device-side normalization would be worth: nothing this
# machine can measure. Written down because the question looks obviously
# worth a yes, and the answer is no for a reason that only a measurement
# gives.
#
# The instrument was to run the attention normalization eight times a layer
# instead of once, on every layer of every token, and see what it cost:
#
#   one normalization a layer      0.385 s generating
#   eight normalizations a layer   0.385 s and 0.388 s generating
#
# Seven extra normalizations of every layer of every token cost nothing that
# shows. So the most that moving them to a device could win is the host time
# they take, and that time is below the floor. TinyLlama is 2048 wide and
# twenty-two deep, so a token's normalizations are about 270 thousand
# operations against 55 milliseconds of generating -- half a per cent would
# be a generous ceiling and the instrument says it is smaller.
#
# There is no round trip to remove either, which is the part that is easy to
# get wrong from an armchair. The normalized vector is uploaded once today; a
# device-side normalization would upload the activation once instead. Same
# bytes, same submission. A normalization can only join a submission already
# happening if its output feeds the next step without coming back, and that
# is chaining machinery built for a gain measured at zero.
#

# submissions a layer bought 0.083 s over seven tokens and twenty-two layers,
# which is about 0.18 ms a submission. A layer still costs four -- the
# queries, keys and values; the attention output; the gate and up; the down
# projection -- and the last three cannot be grouped because each waits for
# the one before. Collapsing those needs the dependent chain to stay on the
# device: the rotation, the attention, the softmax and the residual adds, not
# the normalizations by themselves. That is the shape of the next gain, and
# normalizations are a small component of it rather than a step toward it.
