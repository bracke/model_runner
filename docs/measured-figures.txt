# What the published performance figures were measured against.
#
# The README publishes numbers that were measured, not derived: how long a row
# product takes per element, how long twelve tokens take, how the matrix
# product scales. They cannot be checked the way the conformance figures can,
# because they differ by half a per cent between runs and by much more between
# machines, so no assertion about their value can hold anywhere but here.
#
# What can be checked is whether they still describe this code. Each group
# below names the sources its numbers depend on and a fingerprint of those
# sources as they stood when the numbers were taken. `tests check` recomputes
# the fingerprint and fails when it differs, which means: these sources have
# changed since the figures were published, so either re-measure and record
# what you get, or say why the change cannot have moved them.
#
# That is a duty, and the point of putting it here is that it is a duty the
# release checklist enforces rather than one somebody has to remember. Every
# group below has gone stale once already, by two to four times.
#
# Format, one group per line:
#   <name> <fingerprint> <source> [<source> ...]
#
# The "# covers:" line before a group says which published figures it stands
# for, and the check prints it when that group fails. A group whose figures
# are not named is a group nobody can answer: the reader learns that something
# changed and is left to guess what to measure again. If you add a figure to
# the README, add it to a covers line, and if it depends on a source no group
# lists, list it.
#
# On a mismatch the check prints the fingerprint it computed. Paste that in
# after re-measuring -- not before.
#
# These groups have twice been moved without re-measuring, which the rule
# above allows only with a reason. Both reasons are recorded here, because a
# reason that is not written down is a re-measure that was skipped.
#
# Supports_Batched in Backend.CPU.Describe: Describe had no caller in the
# program at all, so a field in it was not on any path these figures measure.
# Checked by searching the tree for callers, not assumed.
#
# The backend format check in Llama.Resolve: this one does run, once per
# resolved tensor. It runs during Prepare, and neither figure this group
# covers includes Prepare. The twelve-token figure says so outright -- load
# is quoted separately, "because the two are worth separating" -- and the
# batch-size table times prompt evaluation. The change is outside the window
# both figures measure, by their own definitions, which is a better answer
# than a number taken on a machine that at the time was on the powersave
# governor with other work on it.
#
# An A-B build against the previous commit was attempted and abandoned: a git
# worktree cannot resolve this crate's relative path pins.
#
# The capability checks in Llama: the format and alignment checks run during
# Prepare, outside the window as above. The Supports_Batched check runs inside
# it, once per Evaluate_Batch call, so that one was measured rather than
# argued. A-B-A on the same tree, the 131-token prompt with one token
# generated, three runs each: with the check 7.23 7.57 7.60, without it 7.47
# 7.56 7.89, with it again 7.35 7.26 7.76. The whole spread is wider than any
# difference between the states, which is the answer. The published table is
# not contradicted by these: they include load and one generated token.
#
# The Selecting_Backend progress event in Prepare: one Publish per model
# load, outside the window as above. The Prompt_Rendered event is in the
# command layer, which no group here fingerprints.
#
# The memory accounting at session open: a handful of additions, once per
# session, and session open is inside the window the twelve-token figure
# spans. Measured, not argued. A-B-A on the same tree, three runs each:
# with it 8.77 8.89 8.65, without one of the charges 8.73 9.04 9.06, with it
# again 8.71 9.08 8.68. The spread is wider than any difference between the
# states. These runs are on the 131-token prompt and include load, so they
# are not the published figure and are not offered as one.
#
# The session phases: an assignment at each phase boundary, inside the
# window. Measured: with them 8.66 8.35 9.07, with Enter doing nothing 9.09
# 9.38 8.88, with them again 8.84 8.97 9.12. Two evaluator assignments were
# also removed, which is why the middle state is not the faster one.
#
# The replaced-file check in Prepare: one stat of the file, once per model
# load, outside the window as above.
#
# Clearing the token history on reset, and recording a conversion: both
# happen once per reset and once per converted tensor at load, outside the
# window as above.
#
# The rotary pairing choice: two conditionals in the rotary inner loop,
# which is as inside the window as anything gets. Measured: with the choice
# 8.27 9.00 9.09, with the interleaved indices written straight in 9.34 9.28
# 9.04, with the choice again 8.94 9.03 8.86. The spread is wider than any
# difference between the states.
#
# Re-indenting three files to clear compiler style warnings moved all three
# groups at once. Not measured, and not argued either: the release build's
# instructions were compared before and after, and every difference is an
# immediate constant in exception-raising code -- the line number a raise
# reports, moved because blank lines were removed above it. Nothing that
# computes anything changed, which is a stronger statement than a timing and
# cheaper to make.
#
#   objdump -d --no-show-raw-insn obj/release/<unit>.o
#
# Routing every matrix product through the chosen backend: one case per
# product, inside the window. Measured, three runs each: through the choice
# 8.65 9.00 9.14, straight to the pool 8.73 8.97 8.79, through the choice
# again 8.78 8.82 8.84. There are about two thousand products in that run
# and the spread between repeats is wider than the difference between the
# states.
#
# The Capability accessor, read once per request when the batch size is
# clamped: with it 8.59 8.71 8.72, without it 8.65 8.77 8.97, with it again
# 8.76 8.78 8.84.
#
# Anything touching these files that is not outside the measured window gets
# a re-measure like that one, or a comparison like this one.

# covers: the twelve-token figure, the worker-count and share-count
# comparisons, and the batch-size table under "Speed". Re-measure all four
# with `tests speed --model PATH`, which reports the median of three runs of
# exactly the published run and prints a digest of what was generated; the
# batch-size table is the same command with --prompt-file and --batch-size,
# and both commands are printed beside their figures in the README. The
# processor figures come from the operating system's timing tool, as the
# README says.
# 2026-08-11, sliding-window attention. The engine and reference groups both
# list model_runner-llama.adb, which changed: the two attention loops now
# start at the earliest position the window allows instead of at zero.
#
# The figures were NOT re-measured, and the reason is that the change cannot
# have moved them. Every model the published figures were taken on -- and
# every model without an attention.sliding_window key -- has Window = 0, for
# which Earliest returns zero, so both loops run over exactly the positions
# they ran over before and the arithmetic is unchanged. What is added is one
# comparison per head per layer per token: for TinyLlama, 32 heads times 22
# layers, against something over a billion multiply-adds for the same token.
#
# Not re-measuring is a judgement, so here is what it rests on and what would
# overturn it: the model those figures need is not on this machine, and
# nothing in this repository may require one. If a windowed model is ever
# measured, it needs its own figures rather than these -- a narrower window
# does less arithmetic per token, so it would be faster, and none of the
# numbers below would describe it.
# 2026-08-11, mixture of experts. The same two groups again, and the same
# judgement, for the same reason: a model without expert metadata has
# Experts = 0, and every one of the additions is inside a branch on that.
# The dense path runs the products it ran before, in the order it ran them,
# with the loop bounds it had. What is added to it is one test of an integer
# per layer per token. The figures were NOT re-measured and the model they
# need is still not on this machine.
#
# A mixture model would need its own figures and could not use these: it
# runs its feed-forward block a position at a time rather than a batch at a
# time, and it runs several experts where a dense model runs one block, so
# neither the twelve-token figure nor the batch-size table would describe it.
# 2026-08-11, rotary scaling. This one touches code every model runs, not a
# branch a model opts into, so the reasoning has to be arithmetic rather than
# "it is behind an if".
#
# Per rotated pair the rotation now does: one more multiply to form the
# stretched angle, a mix of two angles whose weight is loop-invariant and zero
# for an unscaled model, and two multiplies applying a magnitude that is one.
# Call it six floating-point operations a pair, against the power, the cosine
# and the sine that pair already costs -- on the order of a hundred cycles.
# For TinyLlama that is 36 heads by 32 pairs by 22 layers, about 25 thousand
# pairs a token, so the rotation is under one percent of a token's work and it
# grew by a few percent of that. The published figure is a median of three
# wall-clock runs; this is two orders of magnitude below what that can see.
#
# The figures were NOT re-measured and the model they need is still not on
# this machine. This is the third such note in a row and they are cumulative:
# taken together the three changes add, to a model with no window, no experts
# and no scaling, one integer test per layer per token, one more per layer,
# and the six operations above per rotated pair. Still nothing a stopwatch
# reaches. If that stops being true, the note has to become a measurement.
# 2026-08-11, separate key and value head widths. The cache is now two
# widths rather than one and the attention loops index it with two strides.
# For a model where the two widths are equal -- every model these figures
# were taken on, and every model that states neither width -- the strides are
# the strides that were there, the loop bounds are the bounds that were
# there, and the value cache is the size it was. What is added is one more
# multiply per layer per token to form the second base offset.
#
# The figures were NOT re-measured, and the model they need is not on this
# machine. A model whose value heads are wider would hold a larger cache and
# do more work per position; these figures would not describe it, and it
# would need its own.
# 2026-08-11, qwen3 and qwen3moe. Two architectures added to an enumeration
# and one new thing computed: a normalization of each query head and each key
# head before the rotation. That runs only for a model whose architecture
# has it -- the gain is null for llama and qwen2, and the call is behind a
# test of that -- so a llama model, which is what these figures were taken
# on, does one null pointer comparison more per layer per token.
#
# The figures were NOT re-measured; the model they need is not on this
# machine. A qwen3 model would need its own: normalizing every head is a pass
# over the query and key projections that a llama model does not make.
# The engine and reference groups list quantization.adb, which gained two
# formats as two branches of a case that dispatches by format. A model in
# any other format never enters them. Not re-measured, and the model those
# figures need is still not on this machine.
# The engine and reference groups list llama.adb, where the attention of one
# position moved out of both evaluation paths into a procedure of its own and
# a second was written beside it for the halved cache. The exact path does
# what it did -- same loops, same bounds, same arithmetic -- now behind one
# call per position per layer, which is a call against a head's worth of
# multiply-accumulates. The default is unchanged and the model these figures
# need is still not on this machine.
# 2026-08-11, the embedding command. llama.adb gained an accessor that copies
# the final hidden state out of a session; nothing on the evaluation path
# calls it and nothing else in the file changed. Not re-measured, and the
# model those figures need is not on this machine.
# 2026-08-11, adapters and the grammar. llama.adb gained a merge that runs
# once at load and touches no evaluation path, and one field recording how
# the weights were packed. The generation loop gained a test of a null
# reference per token, and the whole grammar filter is behind it. Neither
# figure is taken with an adapter or a grammar. Not re-measured, and the
# model those figures need is not on this machine.
# 2026-08-12, batched embedding. llama.adb's batched evaluation gained an
# optional buffer of every position's hidden state, written only when a
# caller passes one; generation passes none. Nothing else on either path
# changed. Not re-measured, and the model those figures need is not on this
# machine.
# 2026-08-12, saved contexts. llama.adb gained a snapshot of the committed
# cache and a reader for one back. Neither is on any evaluation path: one
# runs when a caller asks for the bytes and the other before a prompt is
# read. Not re-measured, and the model those figures need is not on this
# machine.
# 2026-08-12, what a merge does to a model's identity. llama.adb records a
# digest of each adapter merged and the fingerprint mixes it in. Both run at
# load and neither is on an evaluation path. Not re-measured, and the model
# those figures need is not on this machine.
